# CONSOLE-SECURITY-A1 — Idempotency & Delivery Guarantee

## Identifiers (kept distinct)
- `requestId` — one HTTP request.
- `correlationId` — links a distributed administrative action chain.
- `sessionId` — the authenticated session (`sha256(token)`).
- `operationId` — the future durable Operation domain (not used here).
- `eventId` — one canonical audit record (server-generated `gen_random_uuid()`).
- **`idempotency_key`** — one audit SUBMISSION. Generated by the Console `GatewayAuditRepository`
  (`randomUUID()`) per `append()` and reused across the adapter's internal retry. It is **NOT** the
  eventId, requestId, correlationId, or operationId.

## Mechanism
`operator_audit_log.idempotency_key` has a partial-unique index; the ingest uses
`INSERT … ON CONFLICT (idempotency_key) WHERE idempotency_key IS NOT NULL DO NOTHING RETURNING …`.
On conflict (no returned row) the handler selects the existing row and returns
`persisted:true, duplicate:true` with the SAME `event_id`.

## Semantics (honest)
**AT-LEAST-ONCE delivery + IDEMPOTENT persistence.** Repeated delivery of the same
`idempotency_key` never creates a duplicate row. A new lifecycle transition under the same
`correlationId` uses a NEW `idempotency_key` → a separate record.

Example: `correlation=C1` → AUTHORIZED (submission S1) → COMPLETED (submission S2). Retry S1 → no
dup; retry S2 → no dup; S1 and S2 are distinct rows sharing C1.

**We do NOT claim exactly-once delivery** and do NOT claim distributed atomicity.

## Live proof
Two POSTs with the same `idempotency_key` → first `duplicate:false`, second `duplicate:true` with the
identical `event_id`; `SELECT count(*) … WHERE idempotency_key=…` returned **1**.
